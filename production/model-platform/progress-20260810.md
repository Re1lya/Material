## 9. 尚未完成和已知风险

### 9.1 单机故障边界

Artifact Keeper、Gitea、Argo CD 及数据库均固定在 `server-00`。有状态数据位于
`/dev/md0` 上的本地目录；Argo CD 自身无 PVC，期望状态保存在 Kubernetes CRD
中。Pod 重启和节点重启能够恢复，但以下故障当前不能自动容忍：

- `server-00` 永久损坏。
- `/dev/md0` 或其 RAID0 成员盘损坏。
- 主机目录被误删或文件系统损坏。

PV 的 `Retain` 只防止 Kubernetes 自动删除目录，不等于备份。

### 9.2 网络和身份

- Artifact Keeper `30670` 和 Gitea `30081` 当前是可信内网 HTTP。
- 尚未配置内部 DNS、TLS、统一身份或入口级限流。
- Runtime Token 尚未按生产流程创建和轮换。
- Artifact Keeper NodePort Service 需要纳入声明式版本控制。
- Argo CD UI 当前仅 ClusterIP，尚未接入内部 DNS、TLS 证书和统一身份。
- Argo CD 已有首个 Gitea 只读机器凭据；Token 轮换和吊销流程尚需固化。

### 9.3 容量和资源

- `/mnt/data` 当前仍有约 1.6TiB 可用，但 RAID0 和共享 ext4 没有项目级硬配额。
- Artifact Keeper 430GiB repository quota 是主要应用级保护。
- CPU requests 已比内存更紧张，后续每部署一个控制面模块都应重新观察节点
  requests、limits 和实际用量。
- OpenSearch、扫描与 SBOM 分析暂未启用，因此当前并不是 Artifact Keeper 的全功能
  安全扫描版本。

### 9.4 平台链路

- Gitea 和 Argo CD 已完成一个 ConfigMap 级最小闭环及更新/回滚验证；Gitea 到
  Tekton 的 main push 校验也已完成，但 ModelVersion、Runtime Profile 和部署意图
  尚未进入完整 schema/引用校验。
- Tekton 和 Crossplane Core 的生产版本、内部镜像、资源和权限已经固化；Crossplane
  Composition/Function 与 Backstage 仍未部署。
- ModelVersion 和 ModelRuntimeProfile 当前只是 Git 目录对象，相关 CRD 尚未安装。
- Qwen3.6 还没有从 Artifact Keeper 缓存到 NPU 节点并用新平台声明启动。
- 没有完成“Artifact Keeper → 缓存 → 推理 → 健康检查 → 最小对话”的生产端到端
  验收。

## 10. 对现有工作负载的影响控制

本阶段遵循以下约束：

- 没有删除、缩容或滚动现有 namespace 中的工作负载。
- 没有创建任何请求 NPU 的新 Pod。
- Gitea 和 PostgreSQL 仅调度到 `server-00`，不调度到 ARM64 NPU 节点。
- Argo CD 运行组件仅调度到 `server-00`，没有向其他 namespace 同步资源。
- Tekton 控制面和 CI Listener 仅调度到 `server-00`；CI Runner 不挂载 Kubernetes
  API Token，所有 Tekton/CI namespace 均无 PVC 和 NPU request。
- Crossplane Core 和 RBAC Manager 仅调度到 `server-00`；没有安装 Provider、Function、
  Configuration 或 Composition，没有 XR、PVC、缓存 Job 和 NPU request。
- 首个 Argo CD Application 仅人工同步一个隔离 ConfigMap；更新、回滚和恢复均固定
  Git SHA 且使用 `prune=false`，没有 Pod、存储、Secret、自动同步或 self-heal 行为。
- 镜像预拉取和部署均使用内部 Registry，不改变现有 Registry 服务。
- Gitea 使用独立 namespace、Service、PV、PVC 和主机目录。
- 使用 `30081` 作为 Gitea HTTP NodePort；该端口不得再用于旧 POC 的临时模型
  port-forward。
- 模型缓存和端到端 NPU 测试保持未执行状态，等待明确的资源窗口。

## 11. 推荐后续顺序

### 阶段 A：完成 Git 事实来源，不使用 NPU

1. 将本目录提交到 GitHub Material，保留设计、部署清单和验收记录。
2. 在现有 Tekton CI 中补充 schema、摘要和引用一致性校验。
3. 把 ModelVersion、RuntimeProfile 和部署意图作为可审计对象推入 Gitea。
4. 在已有禁止 force push 的基础上增加受控写入与独立评审身份；此阶段不下载模型、
   不部署推理。

### 阶段 B：接入生产控制面，不使用 NPU

1. 保持首个 Application 为人工同步，不启用 prune 或 self-heal。
2. 评审第二个低风险目录和资源白名单，验证更新、回滚和监控。
3. Crossplane Core 已完成；下一步固定并镜像 Composition Function，建立 v2
   Pipeline-mode Composition，只做无 XR 的渲染验证。
4. 增加 ModelVersion、RuntimeProfile schema 与引用校验后，再让 Argo CD 人工同步
   独立控制面目录；仍不启用 prune/self-heal。
5. 将需要节点写盘或 NPU 的对象放在独立目录和人工审批门后。

### 阶段 C：模型缓存验证，不申请 NPU

1. 创建 repository-scoped、read-only Runtime Token 和 Kubernetes Secret。
2. 确认 `a3-server-00` 磁盘空间、目录权限和当前网络负载。
3. 人工批准后运行一次 ModelCache Job。
4. 验证 24 个文件、整体 manifestDigest、原子目录和 `READY` 标志。
5. 重跑 Job 验证缓存命中，不重复下载完整模型。

### 阶段 D：NPU 空闲窗口中的端到端验证

1. 再次确认 Device Plugin、NPU Exporter、CPU、内存、磁盘和卡组状态。
2. 使用已认证的 Qwen3.6 Runtime Profile 创建独立测试部署。
3. 只读挂载经过校验的节点缓存，不直接从 Artifact Keeper 边下载边启动。
4. 验证 `/healthcheck`、`/v1/chat/completions` 和最小真实对话。
5. 验证停止、重新启动、失败回滚和缓存复用。
6. 验收后再把已建立的 Crossplane/Tekton 控制面接到运行链路，最后接入 Backstage。
