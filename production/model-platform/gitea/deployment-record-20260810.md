## Scope

Only Gitea and its standalone PostgreSQL were deployed. No Crossplane, Argo
CD, Tekton, Backstage, model cache Job, inference workload, or NPU resource was
created by this stage.

## Deployment shape

- Namespace: `gitea`.
- Helm release: `gitea`, revision 2, status `deployed`.
- One Gitea Deployment and one PostgreSQL StatefulSet.
- Both workloads are selected to `server-00` and `linux/amd64`.
- Gitea requests 500m CPU and 1Gi memory.
- PostgreSQL requests 250m CPU and 512Mi memory.
- Neither workload requests an Ascend or other NPU resource.
- Valkey, PostgreSQL HA, SSH, public registration, and Gitea Actions are
  disabled.
- HTTP is exposed on the trusted internal network at
  `http://110.120.0.3:30081/`.

Revision 2 added the label `otelcol=prometheus-otelcol` to the ServiceMonitor.
It did not recreate either application Pod.

## Credentials

Credentials were generated on `server-00` and written directly to Kubernetes
Secrets. No credential value is present in this repository or Helm values.

- `gitea-admin-credentials`: `username`, `password`.
- `gitea-postgresql-auth`: `postgres-password`, `password`,
  `replication-password`.

The Gitea administrator password mode is `initialOnlyNoReset`. A future password
rotation must update both the Gitea account and the Kubernetes Secret through a
controlled operation.

## Known boundaries

- The endpoint is trusted-network HTTP, not TLS.
- This is a single-host deployment and does not survive loss of `server-00` or
  `/dev/md0`.
- Cache and queue use the single-instance memory/level backends to avoid an
  additional Valkey cluster. Repository and database state are persistent.
- Backup, internal DNS/TLS, SSO, and off-host recovery remain later hardening
  tasks.
